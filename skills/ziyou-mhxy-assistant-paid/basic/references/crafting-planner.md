# 玄灵珠：20格问题的条件解法与手工续算

核验2026-10-07 UTC，普通电脑版时间服。新增入口是Skill宿主/已有Python3.9+的离线工具，不是网页合成表单，不连接或操作游戏。

## 先回答真正的问题

如果目标是从空散珠库存合一颗6级珠，而且本节配方、每珠一格、另留一个输出格、材料可用和补料/合成路径在当前游戏确实适用，那么不必先装齐所有一级珠：按“把一个子材料做完再做下一个”的顺序，峰值是11颗珠加1个输出预留，共12格。20格在这个条件模型里够用。它不证明当前道具和行囊合计20格都可用于合成，也不证明最少跑动。

例：做6级所需的三个5级珠时，每完成一颗就保留；每颗5级先逐个做好三个4级，再补该次额外的2级珠。三个5级完成后，保留它们并补最终额外3级珠。不要一次买齐一级材料，不把已做好的兄弟材料再消费掉，不盲目重做整组。

本工具默认给5段只读检查清单：分别做并保留3颗5级珠，补最后的3级附加珠，再尝试6级。没有要求389个逻辑动作逐一发消息。完整审计轨迹另列每一步材料、假设成功后的各级数量、占格与配方材料守恒。261颗一级与128次成功合成是此空库存**全成功路径**的数值；2/3级是否必成未核实，因此它们不是确定采购单、期望值或有限最坏上限。只有在实际观察到失败后，才按真实库存补缺。

第一轮最多先问两个会改变结果的问题：散珠还是装备逐级镶嵌？现有各级同效果珠和实际可用格是多少？有已给数据不重问。其余运行条件先列为待核实，不要求玩家先写JSON或测试性消耗物品。未确认时直接给上述条件结果和检查要点，不能把演示交成“照做必成”的现场指令。

## 事实、历史观察与模型分开

- 官方2023-12-12基础介绍：三个同效果珠成功合成升一级，最高8级，并有历史失败说明。官方2024-05-20公告对应5月21日调整：制作4–8级必成，制作5/6/7/8级额外消耗同类型2/3/4/5级各一颗。下列完整配方是两份官方说明的组合推导，须核对当前界面材料资格
- 研究时实际看过2024-03-24视频的19/31/40/45秒画面：商人旁购买和合成窗口共存、材料分别占格、出现成功消息。这是历史观察；没有证明2026仍可用，更没有验证低阶成功率、仓库读取或批量购买上限
- 模型固定每颗一格，选中材料不腾空间，始终另留一输出格；“一格足够”也须当前确认。没有依赖仓库或远程合成窗口
- 用户确认单独保存来源、时间、区服、效果以及目标/容量/取得等级范围。历史视频不能替代用户当前确认，示例不能变成用户库存
- 手续费、体力、价格、商人存货、低阶概率仍未知。本工具不计钱、不下单；每次实际操作前看当前材料/费用/体力/资格提示，玩家自行决定是否执行。不要为了验证规则让玩家做未要求的付费实验

官方来源：[玄灵珠获得与合成](https://xyq.163.com/2024/hjzlp/)、[2024高阶调整](https://xyq.163.com/news/20240520/4999_1156134.html)。历史观察：[2024-03-24合成小妙招](https://www.bilibili.com/video/BV1ix4y1U7fE/)。读取核验2026-10-07，不代表全量核对了其后每条维护或实测当前客户端。

## 配方和容量证明

配方：2←1+1+1；3←2+2+2；4←3+3+3；5←4+4+4+2；6←5+5+5+3；7←6+6+6+4；8←7+7+7+5。效果一致、同级基础材料有效性由当前界面确认。转移锁不在数量模型中自动合并；玩家必须只放入本次可用珠，输出继承最长锁的官方规则仍适用。

空库存的子树峰值P(1)=1，P(g)=各第i个子材料的“已保留i颗+P(子材料)”最大值，i从0起。等级1–6的P为1、3、5、7、9、11；再加输出预留1格，6级为12格。每次获得/成功合成都逐步核对占格。材料的一级等价值为1、3、9、27、84、261、810、2514；成功守恒，不是货币价值。

如果某次2/3级操作后实际清点发现恰好损失一个输入、另两个仍在，保留两个幸存者，只补丢失的那个。2级局部峰值2+1=3，3级为2+3=5，不增加原峰值；有限次数这样的失败不会增加12格的条件容量界，但并不保证有限次结束。没有实际观察时，不假定失败会这样扣料。其他结果立即暂停核对。上述12格证明针对空库存路径；如果起初已有中间珠，损失它后重做的子树可能比原路径更占格。例如总容量4格、已有3颗2级，原本可直接尝试3级；失败剩2颗2级后，重做缺的一颗会超出4格。工具在每次观察到损失后都重新检查完整路径，卡容量就停止交接。

已有库存也占格；高于目标的珠不会自动拆解，锁住或其他效果的珠不能混入可用库存。无关物品的占格先从capacity扣除。若只有“20空格”和已有珠，capacity应是这次可用同一库存范围内的已有珠格加空格，不能把20误当总格或反过来；多背包的可用性必须核对。

此深度优先顺序不是全局最少格/最少搬运优化器。若某组已有库存下此顺序卡容量，工具输出可行前缀和阻塞点，但不交接下一步花费动作。玩家可先明确可转存的物品并提供新的实际库存，工具不自动转存。不能将被阻塞路径的前缀计数说成全部材料数。

## 输入（宿主整理，玩家不必写）

examples/crafting-20-slot-scenario.json是空库存条件演示。必填：

- schema=mhxy-crafting-config/v1，ruleset=pc_time，server和bead_type为明确文字
- objective=loose，仅一颗散珠；target_grade为2–8，不支持已装备逐级镶嵌
- capacity为1–200整数，是扣除无关物品后的本流程总可用格
- inventory为1–8级计数；实际观察必须八级都明确填写，零也要写。缺级不猜零。场景示例才可稀疏输入
- as_of及来源observed_at为严格UTC时间；库存来源不能来自as_of之后。跨日旧库存只作演示，需重新清点。为保留可重算历史，程序不读取系统时钟；“当前”只相对于所填as_of。现场使用前宿主必须确认as_of确为本次当前时点，不能把整份日期一致的旧会话当成今天已检查；重开应先用新的实际观察refresh，不改旧来源日期
- inventory_source={kind,server,bead_type,observed_at,note}；kind为scenario或user_observation，后者只能用于用户明确报告的实际清点
- acquire_grade默认1；设3时，缺的3级及配方所需2级直接列“手工取得需求”，不把低阶必成当作事实。已有1/2级仍保留占格，不自动丢弃。不是假定商人出售3级：在哪里能取得由用户确认，不能据此购买

confirmations可省略。若要逐步现场交接，各CHECKS键需status=user_confirmed、独立source和scope。scope固定绑定ruleset/server/bead_type/target_grade/capacity/acquire_grade，可由confirmation_scope(config)生成，但必须先有用户真实确认，宿主不能自己填“已确认”。键为：current_recipes_match、compatible_inputs、usable_capacity、one_bead_per_cell_safe、one_output_cell_sufficient、manual_access。确认来源必须user_observation、区服/效果相符、不晚于as_of，且同一UTC日；玩家每次操作仍在游戏里检查实际材料/费用/体力/资格，不需要每次向Skill单独发消息。

更改目标、类型、区服、capacity或acquire_grade需要新配置、新清点与新范围确认；旧会话另存，不改旧initial或历史事件来伪造续算。来源标签只能验证结构和一致性，不能证明话是真的或确认仍未被现实变化影响。

## 默认分段使用，避免389次聊天确认

默认报告直接附目标所需的紧凑配方阶梯：例如6级路线列2←三个1、3←三个2、4←三个3、5←三个4加一个2、6←三个5加一个3；同时写清先逐个完成三个基础材料，再补附加珠。无需打开389行细轨迹才能知道“子材料”是什么。官方组合推导来源、当前低阶结果未知、兄弟珠保留和输出格预留都随报告显示。acquire_grade=3时，2/3级标为直接取得，不误引导重新从一级合起。

分段是阅读整理，不是游戏批量功能，不减少游戏本身的购买或合成点击。每一段只显示条件总量、预计检查点库存和容量峰值；总量绝不是让玩家一次买齐。按子材料逐个完成，途中每次看游戏结果。发生失败、数量偏差、窗口/条件变化或结果不明，立即停段，不继续照后面的预计数走。

玩家可到选定检查点才报告完整实际库存，用refresh保存新观察、重新规划后续。这不会默认中间全部成功，也不会按预计数量扣库存；实际数量不同仍以实际为准并重核条件。未开始逐步审计时没有待观察动作，不必制造125条假想成功事件。若已经begin了某一步，refresh仍须resolve_pending=true和完整观察才能结束它。

未确认运行条件时这5段同样只是演示，不成为现场执行保证。宿主先展示最短有用清单，有需要再打开--detail steps。read_only_checkpoints均标actually_completed=false，inspect不据此推进状态。

## 可选逐步审计：保存、暂停与恢复

scripts/crafting.py的会话是单文件源记录，schema=mhxy-crafting-session/v1；包括初始配置和事件，没有可信缓存。inspect每次重放并重算，不把上次的预计库存当实际库存。保存文件不覆盖旧版本。

1. start(config)建会话；inspect(session)取revision、plan_token、当前库存、待观察动作和条件演示。检查未通过时next_action为null；示例只能看演示
2. 玩家决定尝试当前一步，并已核对本次材料、价格/费用、体力与资格后，begin(session, expected_revision, plan_token, manual_check)记“待观察”。manual_check使用该用户当次检查的source，不可用模型自述充数。begin只记记录，不执行、支付或移动游戏物品；目标变化、旧revision/token、容量不足或未确认均拒绝
3. 手工动作后，reconcile(session, expected_revision, observation)。observation包含outcome=success/failure/unknown及source。success/failure必须完整inventory（八级都明确），不能只报变化的那一级。成功仅在实际清点等于配方结果时推进
4. unknown时inventory省略或null，保留原库存和待观察动作，禁止开始另一操作。回来后仍需实际完整结果；禁止自动套用成功图
5. 2/3级失败只有在本次清点与“恰少一个输入、其余不变”完全一致时，才识别这个分支并从真实库存补一颗缺料。其他失败、意外增减、4–8级失败或成功标签与数量不符，保存新观察但清空条件确认、暂停
6. 外部取出/放入、意外消耗或中断后库存改变，refresh提供完整当前inventory/source；默认清空旧确认。要恢复现场交接，重新提供有范围的confirmations。若尚有待观察动作，必须resolve_pending=true明确以这次完整清点结束它，不能默默丢弃未决结果。事件保留以供追溯
7. 费用/来源/容量等现实条件已变但还没清点，先停下。refresh不修改目标/容量；这些变化另建新配置。达到目标立即不再给动作

所有API返回新对象，不修改调用者数据。revision防误用旧分支；摘要防普通状态错配，不是身份认证或加密签名，也不能阻止有人故意改写整份原始历史。

## 命令

在包根目录使用已有Python3.9+，无第三方依赖、不自动安装。输出必须是新文件：

    python -X utf8 scripts/crafting.py examples/crafting-20-slot-scenario.json --kind plan --format text
    python -X utf8 scripts/crafting.py examples/crafting-20-slot-scenario.json --kind plan --format text --detail steps
    python -X utf8 scripts/crafting.py examples/crafting-20-slot-scenario.json --kind start --output new-crafting-session.json
    python -X utf8 scripts/crafting.py new-crafting-session.json --kind inspect --output new-crafting-inspection.json

begin输入为{session,expected_revision,plan_token,manual_check}；reconcile输入为{session,expected_revision,observation}；refresh输入为{session,expected_revision,observation,confirmations?,resolve_pending?}。输入可由宿主构建后调用同名--kind，输出为新会话。--format text默认导出易读分段演示，--detail steps导出完整细轨迹，但用于继续的源会话另存JSON。

边界：输入4MiB、最多10000事件、单次配置最多200格、目标8以内；超限拒绝。继续很长的实际流程时保留旧会话，重新清点再建新会话；不自动截断历史。不读取网络、游戏、动态插件、输入指定脚本或外部库存文件。

## rc6性能与记录完整性

重放会话时，仅对同一规划范围与完全相同的八级库存复用容量运算；所有事件仍逐条核对来源、时间、完整库存、未决动作和确认时效。观察备注或时间变化不会重复生成同一条长轨迹，库存数量变化会重新检查。缓存只在本次重放内存在，不保存为事实、不跨会话复用、不丢弃历史。
