# 从一个问题到可更新的完整决策档案

本版本目标：现有角色的有限预算升级，或保留/自升/换成品。不是全门派战斗排名服务，不自动获取行情。用户对自然语言提问；宿主负责读事实、整理输入、运行脚本与解释。不要先要求玩家写 JSON。

本工作流仅用于确需连续预算/状态联动或可重开更新的完整决定。已有可靠事实/规则直接短答；独立计算使用最小对应工具；有依据的简单算术可用最小通用计算校验。没有某项精确计算能力只阻断该未知结论，先答其余可靠子问题；不为了跑工具让玩家重抄截图、补无关区服或写JSON。

日常介绍沿用GUIDE.md和README.md，只说明功能与使用方法；本工作流按当前问题保留具体条件与缺口，不延伸为整个产品的可靠性评价。

## 1. 先抓住真正的决定

“下一笔钱花哪”先确认主要活动/当前痛点与本次新增预算（货币）。不是每个用户都需要全号诊断。已给资料先利用，最多直接索取2个决定性缺失信息槽；按实际请求的信息槽计数，不按句子、问号或编号计数。玩法、用途、旧属性、宝石是4槽，不能塞成两句。已给、图中可见和已更正事实不重复问；旧图仅在比较换装提升时标为可选，不要求另抄图中宝石。优先让玩家直接粘贴已有物品/报价文字，宿主自行整理，再补最影响选择的一项；不要求首轮交全号/全部宠物资料。先给可确定的结论，例如80级普通装备不能打10段，或先卖后买需要等待回款。

按四层拆开：

- 用户明确的当前状态：自己持有的装备、现等级、本级进度、余额
- 候选目标：看到的商品、示例角色、别人方案；不能视为用户现状
- 条件：只为算例选的起点、尚未成交卖价、尚未确认的道具经验
- 公开规则：附规则ID/第一方URL与核对日，旧页面不是对当前全部机制的保证

原话里的“举个6段的例子”和“我的灵饰要不要上7”不证明自己的灵饰是6段。能算单颗7级材料，但实际新增逐级采购须知道起点；也可以明确“若你现在是6段”给条件结果。

## 2. 事实账本校验

对会改变建议的事实，宿主准备 `scripts/evidence.py` 输入；结构见 `examples/evidence-owned-vs-example.json`。

- sources: 每段原文的 id、origin（user/external/official_reference/demonstration）、text
- facts: id、label、scope（current_account/current_item/candidate/general_rule/example/scenario）、status（confirmed/conditional/unknown/conflicting）、value、evidence
- evidence 是 source_id 和原文 excerpt；必须是来源中的逐字片段
- conditional 还须写 assumption；unknown/conflicting 的 value 必须是 null
- calculation_input 与 bindings 可把 `/currentForge` 之类 JSON 路径绑定到 fact_id；值和类型必须完全一致，不自动改单位

运行：`python -X utf8 scripts/evidence.py evidence-input.json`。当前物品/角色的确认事实不能来自外部资料或演示，不能用示例填空。

此工具只核对来源结构、原文匹配和绑定值一致，不证明原文语义、真伪或截图理解正确。用户消息里的转引仍须单独标为 external/demonstration；不能把整段都标 user 来规避区分。输出未验证的绑定仍需宿主复核。

## 3. 宝石自升 vs 换成品：一条完整路径

用 `python -X utf8 scripts/plans.py input.json --kind gem_upgrade`；从 `examples/plan-gem-upgrade.json` 理解字段，示例金额全部为合成测试单位，两的标签不代表真实市价。

必填：context、equipment、grade_quotes、owned_stones、fees。equipment 沿用 routes.gem_feasibility 字段，核对原装备等级、部位、当前/目标锻数、已镶宝石和特效。grade_quotes 按每个新增等级记录完整人工报价。owned_stones 按等级记录 quantity 和 opportunity_quote。库存仅抵一颗同级同类石，不自动合成、拆分或抵现金。

可选 `decision_objective` 放在gem_upgrade输入顶层，只接受 `upfront_cash`（立即新增现金优先）或 `economic_cost`（经济成本优先）。宿主依据用户明确优先级设置；报告不从title、basis、备注等任意自由文本自动推断。字段省略时保持旧输入兼容，采用平衡展示并列可验证结果；`null`和显式`balanced`均非法。选择目标只改变结果重点，不变更公式、资格、预算、来源和时效要求。

输出同时给：

1. 资格是否成立；禁止跳级/超上限或第三种宝石
2. 全部新增等级采购清单，不仅最高级一颗
3. 新增现金、库存机会成本、经济成本、剩余预算
4. 可选同目标成品的先买现金、条件卖旧后净成本与成品价格临界线
5. 结论、前提、不可行动原因、具体下一步

replacement 的 purchase/fees/old_item_resale 沿用 decisions.upgrade_compare，另需 eligibility（confirmed/unknown/ineligible）和 equivalence（status=confirmed/unknown/different_target，basis说明同目标的依据）。同目标必须核对底子、附加属性、套装/特效与修理状态，不能只比锻数。不同目标保留对照，不排序谁值得。

fees 空列表表示明确确认没有额外费用；未知费用必须填一行 quote=null。未成交收入不扣先买现金，历史已花金额可放 sunk_cost，只作提示，不重复收费。报价过期不得用于依赖该报价的当前购买建议。逐结论检查依赖：有效当前现金比较不受无关旧机会值/旧装估值阻断，经济成本和卖旧后净成本仍保留相应过期/未知限制；不能因为现金可比而放松资格或同目标证据。材料合成下限只供核对，不能乘一级报价后称预计采购成本。

## 4. 普通点修与道具混用

`python -X utf8 scripts/plans.py input.json --kind training_mix`；示例 `examples/plan-training-mix.json`。

在普通修炼已核验XP和10XP购次上，枚举道具颗数，普通购次补足，精确比较每种现金。输入 context、cultivation、item_xp、item_xp_evidence、item_quote、mixing_eligibility；可选 max_items 作为本次确认可用颗数上限。

不从金丹品质推经验；每颗实际XP与道具/普通修炼均可用须用户在游戏中确认。先做普通部分再用道具补尾段的顺序也只在混用资格成立时可用。资格、每日限制或来源未知就保持条件结果。最多100,000颗枚举，超出返回输入错误，不输出截断“最优”。

合成算例：0到9需5190XP；假设每颗50XP、每颗140000两，103颗+4次普通购次为14540000两，比104颗纯道具少20000两。这个金额只是合成报价，不是市场行情；全普通为15570000两。脚本会重算其他XP、进度和价格，不内置该答案。

## 5. 跨系统、共享预算的完整计划

`python -X utf8 scripts/portfolio.py input.json --format text --output new-plan.txt`；JSON输入可保存重开，示例 `examples/plan-whole-budget.json`。普通用户不必操作命令；宿主整理运行并交付输入档案+易读报告。

适合已能枚举明确整项目标的情境，例如“鞋子升到10段、指定人物修炼到9、预留修理消耗金”。每个目标必须有用户依据；不把“适合109大唐”转换成虚构面板门槛。

- context：同服、同币种、核价日
- budget/reserve：本次可支配现金与不动用的预留金；不抵未成交收入
- 可选 system_budgets：按options.system指定同币种的独立分类上限，例如装备3000、宝宝800。自动汇总对应项目现金，不可互相挪用；分类上限与全局预算/预留同时满足。未列类别会明确提示仅受全局预算约束，不自动分配余额。上限名称与任何项目system都不匹配时拒绝，避免拼写错误使专款限制失效
- goals：id、target、basis；already_met 记录当前已满足目标；completed_options 记录用户明确已执行项目（不重复收费/耗库存，可满足前置与其目标）
- options：最多16个整项项目，每项 id/label/system/goals/costs/eligibility/effect_basis/requires/conflicts/consumes；可选 route_group/owned_materials
- costs 与 owned_materials 用含完整元数据的人工报价行；固定规则费用由实际脚本计算后记录来源，不能抄估算凑账
- requires：先完成的项目ID；conflicts 或相同 route_group 不可同时选
- consumes：会消耗的共有库存/已确认可操作时间；available_resources 填总库存，防止同一颗石/同一笔资源两次抵扣

只能让效果证据齐全的整项项目进入确切目标覆盖。宝石原始属性不能直接证明人物面板目标，套装/联动必须完整做成候选整项。所列目标按硬约束，不强制用户写偏好权重。

求满足全部目标、预算、依赖、互斥和共享资源的最低新增现金；库存经济成本单独报，不宣称经济成本也最低。保留现状始终显示，已经达标时优先零花费。未知价/资格/过期报价候选留在待核实，不偷偷按0纳入。若没有方案，只能说“当前已确认候选没有证明可行”，不能说整个游戏无解。

同价方案最多展示10条并披露截断，总枚举完整；大于16项明确拒绝，先按有意义的阶段分解。不同货币分档案，不隐式换汇。项目不能在计划里产出未来现金或新资源；这避免循环“卖出后再买”幻想资金。

## 6. 给玩家的最终交付

普通小题用短答。完整决定至少给：

- 建议和可读报告均先回答用户明确的决定目标，再列其他比较口径；未指定时并列可验证结果，不用任意自由文本推断目标。按各结论的实际依赖定位未知/过期限制；说清哪一个缺项会改变哪一个选择
- 当前已知事实、条件假设、仍未确认的事项
- 保留现状与可行候选的新增现金、机会成本、目标差异及前置
- 采购/实施顺序，预留与未计项；目标已达成且无新增材料/未付费用时明确新增0、无需为该目标继续询价采购，不安排无关动作。其他未完成子目标、真实未付费用或状态冲突仍列出
- 价格或事实改变到何种程度应重新选择；能算临界线就给具体临界线
- 可保存输入和计算结果，注明规则版本、核价日与纯手工数据
- 直接影响决定的规则，给玩家可打开的官方链接和逐来源核验日；从该来源记录/对应参考文档就近读取，不能只在内部保留。页面发布日期、全服生效日、来源核验日和本轮计算/查看时点分开；包级增补日、as_of更新和重开失败都不刷新核验日。混合引用不统一成最早或最新日期。标清明确规则与组合推论

不要把工具JSON原样当最终答复；用用户正在作的决定组织。也不要把详细报告强加给只问数量的用户。完整性只限明确列出的目标/项目，未知升级、技能、维护、时间成本要显式列出。

## 继续上一份计划时

保留玩家原来分别给装备/宠物的预算，不因总额够用就互相挪用。上次尚未成交的卖旧款仍不算现钱，只有用户确认已结算并给净到账才更新。重开草稿不能把原核价日当今天：先显示原日期，若要今天采购，更新as_of到今天后重新判断报价年龄，原报价observed_on不自动改写。历史复盘可保留旧as_of，但必须标为历史条件结果。

先用最多一句承接仍未完成目标和当前已知约束；能继续就直接算，不默认每轮必须追问。只在确有本轮决定性缺项时问最多2个信息槽，已给/已更正事实不重问，不从头重填。用户报完所需资料就执行计划，不继续泛泛要“更多截图”。最后交付具体所选项目/数量/顺序、各分类花费与余额、未选项为何暂缓、改变选择的阈值、可保存输入和报告。若仍缺真正决定性报价，只保留那条待核实方案，能算的路线先交付；不以空账本代替结果。

## 价格没问到或预算不够，仍给可执行的边界

新的gem_upgrade输出 replacement_purchase_affordability_ceiling：扣除已知成品购入费用后的先买单价上限，不借用未来卖旧款。若现金侧恰好只有一个未知单价，还给single_unknown_quote_thresholds：预算可承受、自升与成品先付现金相等、条件卖旧后净现金相等、条件经济成本相等四条线。其他费用/目标/库存值或卖旧净回改变时都要重算。多于一个未知价格不硬缩成一个P；库存机会成本不明时只保留能算的现金界线。

临界线同时保留精确分数和接口可填的安全六位小数价（向下取整，单价最高1万亿）。负临界线表示不存在满足该条件的非负价，不推荐负价或虚构折扣。过期价格应另存历史情景；用于今天的缺价版将那条quote保留null，不能把旧300万自动当新价。

replacement可选resale_timing：not_before为最早可卖日期或null，keep_until_replacement为是否必须先拿到替换物再卖旧，basis为用户原话依据。未来解限日与“已结算”互相冲突时拒绝。日期已解限也不证明卖得出，先买现金仍按购入总额计算。工具输出这些约束给宿主，不操作出售或承诺解限后成交。

portfolio还会给target_plans_before_money_constraints：在已列且资料齐全的候选内，先满足目标/依赖/互斥/库存的最低现金组合，再列全局与每个分类预算缺口。这是诊断，不是超预算购买建议；最低原始现金组合不一定是需要最少分类调整的组合。不要仅说“无方案”后让玩家自己算差多少，也不要把诊断里超分类额度的方案当可执行方案。

## 人物等级与装备等级矛盾

玩家已给人物等级时，放进equipment.characterLevel。gem_eligibility会查已核简易降5级、无级别不限制人物等级；普通110装备不因已镶过宝石就让109角色可穿。没有人物等级时，返回仅说明镶嵌/装备本身规则，不证明当前人物可穿。武器造型、性别、门派等其他资格仍须核对。遇到“已核实可穿”与明确等级/特效资料冲突，先指出哪两项不一致并请用户确认，不用一个笼统eligible覆盖它们。

## 图形入口与关联边界

preview/planning.html已经提供完整宝石、混合修炼与共享预算的中文表单，三套输入一次保存，未知值和来源一起保留。它们不互相自动复制成本：共同预算中的整项目报价/效果依据须自己更新。需要一处新事实自动更新多个步骤时，宿主使用单一dossier，并可登记equipment.optimize。完整功能矩阵见feature-matrix.md。
